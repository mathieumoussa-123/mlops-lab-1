## Answer 2

The --backend-store-uri option tells MLflow where to store experiment and run metadata. In this lab, sqlite:///mlflow.db means that MLflow stores this metadata in a local SQLite database called mlflow.db.

The metadata includes information such as experiments, runs, parameters, metrics, run IDs, run status, and other tracking information.

The --default-artifact-root option tells MLflow where to store artifacts produced by the runs. In this lab, ./mlruns means that the artifacts are stored locally under the mlruns directory.

The difference is that metadata describes the experiment and its results, while artifacts are actual files produced or saved by a run, such as the trained model and its associated files.

## Answer 3

mlflow.db and mlruns/ should not be tracked by Git because they are local outputs generated by MLflow during experiment execution rather than source code. They can change frequently and may become large, which would unnecessarily increase the size and history of the Git repository.

They also should not be tracked by DVC because they are not versioned datasets. DVC is being used to version the Food-11 data, while MLflow already has its own system for managing experiment metadata, metrics, and model artifacts.

For this reason, both mlflow.db and mlruns/ were added to .gitignore.

## Answer 5

mlflow.log_param is used for values that are fixed for the entire run, such as the learning rate, batch size, number of epochs, dataset choice, and model architecture.

mlflow.log_metric is used for values produced during or after training, such as train loss, validation loss, validation accuracy, and test accuracy.

A metric can change during training, so log_metric accepts a step value. In this training script, the epoch number is used as the step, allowing MLflow to record and plot how each metric changes from one epoch to the next.

A parameter does not need a step because its value is chosen before training and remains fixed for the run.

## Answer 8

The strongest pattern is that learning rate had a much larger effect on validation accuracy than batch size.

The learning rate of 0.0001 produced the highest validation accuracy at 0.716241, while increasing the learning rate to 0.01 reduced validation accuracy to 0.156022.

For the two runs using a learning rate of 0.001, changing the batch size from 32 to 64 only changed validation accuracy from 0.584854 to 0.592153. This is a relatively small difference compared with the effect of changing the learning rate.

This suggests that, for these runs, the lower learning rate gave better validation performance, while changing the batch size had a smaller effect.
